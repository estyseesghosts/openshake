# OpenShake

OpenShake is a fork of the OpenCode **TUI frontend**. The TUI, its LaTeX renderer, and its
Mermaid renderer are vendored as git subtrees from `anomalyco/opencode`; the server, SDKs, and
theme packages stay as pinned npm dependencies. No monorepo checkout is needed to build or run it.

Fork-local behavior lives in the vendored TUI: a third `medium` verbosity with semantic activity
and edit groups, visibility for failures and singleton diffs, bounds on long-session memory and
streaming churn, a faster startup path, and a `shake` launch wordmark. These changes are carried
on the `tui-fork` branch and merged into `main` as a subtree — see [Branches](#branches).

## Requirements

- Bun `1.4.4` (see `.bun-version`)
- Either a local OpenCode service (`@opencode/cli@2.4.1` is a dev dependency and provides
  `opencode serve --service`), or a reachable remote OpenCode server

## Install, run, and build

There is no separate build or transpile step: Bun runs the TypeScript/TSX sources directly.

```bash
bun install --frozen-lockfile
bun run dev                        # local background service, auto-discovered/started
bun run dev /path/to/project       # same, launching in a directory
bun run start                      # identical to dev
```

To expose the app as a `shake` command on PATH:

```bash
bun run link:cli                   # registers the package and installs a shake shim
shake --help                       # works from any directory
shake --local /path/to/project
```

The shim resolves the repo through `~/.bun/install/global/node_modules/openshake`, so keep `main`
checked out: the executable and first-party host code exist on `main`, not on the other branches.

Remote backend:

```bash
OPEN_SHAKE_SERVER=http://host:4096 bun run dev
OPEN_SHAKE_SERVER=https://host:4096 OPEN_SHAKE_PASSWORD=... bun run dev
# or: bun run dev --server http://host:4096 --username user --password ...
```

`--local` forces the local background service and ignores the server env vars.
`OPEN_SHAKE_CHANNEL` isolates client-local state (tabs, drafts, layout) between different forks or
backends; it defaults to `local`. Debug/info logging is off by default; set `OPEN_SHAKE_DEBUG=1`
to print it (otherwise warnings and errors are buffered until shutdown, so log lines never paint
over the rendered frame).

Settings are stored in `~/.config/openshake/config.json` (override with `OPEN_SHAKE_CONFIG`). The
file is validated against the vendored TUI's config schema on load and on write.

## Branches

| Branch          | Contains                                                                                                                        | Edit directly?                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| `main`          | First-party host (`src/`), tooling (`scripts/`), docs, and the assembled `vendor/` subtree. The branch to run and release from. | Yes — for host code, docs, tooling |
| `tui-fork`      | Pristine upstream snapshot **plus every OpenShake change to vendored TUI/client code**, as ordinary reviewable commits.         | Yes — for all `vendor/tui` changes |
| `vendor-source` | Pristine `git archive` snapshots of upstream `packages/tui`, `packages/latex`, `packages/merman`. Never contains fork changes.  | No — generated by `vendor:sync`    |

`main`'s `vendor/` is a squash subtree merge of `tui-fork`. Never hand-edit `vendor/` on `main`;
the next subtree merge would overwrite it. Make the change on `tui-fork`, commit it there, then:

```bash
git checkout main
git subtree merge --prefix=vendor tui-fork --squash -m 'subtree: sync tui-fork into vendor'
```

See [docs/architecture.md](docs/architecture.md) for the dependency boundaries and the fork
modules, and [docs/decisions/0001-vendor-subtree.md](docs/decisions/0001-vendor-subtree.md) for why
this topology exists.

## Upstream sync

```bash
bun run vendor:sync v2.4.2
```

The script archives the three packages from the upstream ref, commits a pristine snapshot on
`vendor-source`, rebases `tui-fork` onto it, and subtree-merges `tui-fork` into the current branch.
It defaults to a sibling `../opencode` checkout; set `OPENCODE_UPSTREAM` to use another path. This
avoids splitting tens of thousands of upstream commits just to move a snapshot.

If the rebase conflicts, the script aborts cleanly and tells you to resolve them. Do that on
`tui-fork` (`git worktree add ../shake-fork tui-fork`, rebase onto `vendor-source`, fix and
continue), then rerun `vendor:sync` to finish the subtree merge. After a successful sync, bump
`package.json` dependency/override versions and `UPSTREAM_VERSION` in `src/backend.ts`, run
`bun install`, and commit on `main`.

## Version lockstep

The vendored TUI and every `@opencode/*` package plus the server **must** be the same version. The
generated HTTP client and plugin SDK are built from the server's API at that exact commit.
Currently pinned to `2.4.1` in `package.json`, overrides, and `src/backend.ts`.

## Layout

```text
src/            first-party host: backend resolution, config persistence, entry point
vendor/tui/     subtree of upstream packages/tui (fork changes via tui-fork)
vendor/latex/   subtree of upstream packages/latex
vendor/merman/  subtree of upstream packages/merman
patches/        upstream solid-js patch, applied via bun patchedDependencies
scripts/        vendor sync helper and shake launcher
docs/           architecture notes and decision records
```

`src/main.tsx` binds `@opencode/latex/plugin` and `@opencode/merman/plugin` to the vendored sources
with a small Bun alias plugin; `tsconfig` paths alone do not cross the nested package boundary.

## Checks

```bash
bun run verify    # format + lint + typecheck + first-party backend tests
```

Vendored code is excluded from formatting and linting; it is checked with the upstream TypeScript
settings, while first-party code follows `AGENTS.md` and `../typescript-style-guide.md`.
`lint:check` uses `oxlint` because Bun 1.4.4's `bun lint` delegates to a package script. The `test`
script explicitly lists first-party test files; vendored tests require upstream's preloads and are
run separately:

```bash
# pure fork tests
bun test --preload '@opentui/solid/preload' \
  vendor/tui/test/cli/tui/session-verbosity.test.ts \
  vendor/tui/test/cli/tui/medium-activity-summary.test.ts \
  vendor/tui/test/context/message-window.test.ts

# rendered fork tests (both preloads required)
bun test --preload '@opentui/solid/preload' --preload './vendor/tui/test/preload.ts' \
  vendor/tui/test/cli/tui/group-view.test.tsx \
  vendor/tui/test/cli/tui/logo-view.test.tsx
```

Opt-in local profiling (deterministic fixtures; no timing assertions in CI):

```bash
bun run --cwd vendor/tui bench:load -- --sessions 40 --messages 400 --assistants 12 --rounds 200
```
